# Validate

저장소 검사를 실행하고 요청 범위의 실패 원인을 수정한다. 실행·보고만 요청한 경우에는 코드를 바꾸지 않는다.

## 검사 선택과 실행

- 저장소 지침·CI·manifest·스크립트에서 실제 명령과 runtime·package manager를 확인한다. 파일 확장자만으로 검사기를 가정하지 않는다.
- 설정되지 않은 검사는 SKIP으로 보고한다. 검사를 만들기 위해 새 도구를 설치하거나 다운로드형 fallback을 실행하지 않는다.
- 기존 작업 트리와 의존성 상태를 확인한다. 예상 밖 설치·삭제·lockfile 변경은 원인과 요청 범위를 확인한다.
- 운영·사용자 데이터를 쓰지 않는 환경에서 실행한다. 독립 검사는 병렬 처리하되 DB·출력 경로를 공유하면 순서를 정한다.

## 실패 판단과 수정

1. 출력·구현·기대 계약을 대조해 새 회귀, 기존 실패, 환경 문제를 나눈다. 기존 실패라는 판단은 변경 전 상태나 독립 재현으로 뒷받침한다.
2. 가설을 최소 실험으로 확인하고 공통 원인과 연쇄 실패를 구별한다. 관련 없는 업그레이드·리팩토링을 섞지 않는다.
3. 구현이 계약을 어겼으면 구현을 고친다. 테스트·규칙 자체가 틀렸다는 근거가 있을 때만 기대값을 바꾼다.
4. `any`, `@ts-ignore`, skip, timeout 증가만으로 실패를 가리지 않는다. 예외가 필요하면 근거와 범위를 명시한다.
5. 수정한 동작·오류 경로를 검증한다. 외부 경계의 mock은 실제 계약을 따르고 통합 흐름 전체를 mock으로 대체하지 않는다.
6. 수정 후 관련 검사를 재실행한다. 같은 실패의 근거 없는 재시도나 변경 없는 성공 검사의 반복을 피한다.

환경에 막히면 필요한 조건을 보고하고 독립적으로 가능한 검사는 계속한다. 완료 시 명령·PASS/FAIL/SKIP, 수정 원인, 미검증 위험을 요약하고 검사 전후 diff에서 예상 밖 변경을 확인한다.

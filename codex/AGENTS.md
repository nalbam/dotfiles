# AGENTS.md

모든 프로젝트에 적용할 개인 기본값이다. 프로젝트별 구조·명령·관례는 해당 저장소 지침을 따른다.

## Language

- 한국어 존댓말로 결과부터 간결하게 응답한다. 코드·명령어·파일명·API 이름은 원문을 유지한다.
- 커밋 메시지·코드 주석은 프로젝트 관례가 없으면 영어, PR 본문·이슈 코멘트는 한국어로 쓴다.

## Git Safety

- **`main`에 push하거나 `main`을 대상으로 merge할 때만 사용자 승인을 받는다.** 직접 실행, PR merge, 자동 merge 예약 모두 포함한다. 대상과 변경 내용을 제시하고, 이미 승인받은 동일 작업은 다시 묻지 않는다.
- 요청한 목표에 필요한 브랜치 생성·수정·검증·commit·`main` 이외 브랜치 push·PR 생성·충돌 해결·작업 브랜치 정리는 별도 승인 없이 수행한다. push는 현재 브랜치 이름뿐 아니라 원격 목적지가 `main`인지 확인한다.
- 기존 작업 트리·index의 무관한 변경을 되돌리거나 본인 커밋에 섞지 않는다.
- 변경 폐기·이력 정리·브랜치 삭제는 요청 범위와 기존 작업 보존을 확인한 뒤 필요한 경우에만 수행한다. 본인 작업 브랜치의 이력을 다시 push해야 하면 원격 변경을 확인하고 `--force-with-lease`를 사용한다.
- 커밋 메시지·PR 본문에 `Co-Authored-By`, `Generated with`, 도구 귀속 푸터·배지를 넣지 않는다.

## 작업 방식

- 복잡한 변경은 목표·범위·완료 기준과 검증 방법을 짧게 공유한다. 단순 작업에 별도 계획 절차를 강제하지 않는다.
- 요청한 목표에 필요한 조사·구현·설정 변경·검증은 중간 확인 없이 완료한다. 되돌릴 수 있는 선택은 기존 관례와 합리적인 가정으로 결정하고 결과에 설명한다. 사용자만 제공할 수 있는 필수 정보가 없을 때만 질문하며, 답변 없이 가능한 작업은 계속한다.
- 이미 받은 권한과 결정은 유지한다. 이 자율 수행 권한은 요청 범위 안에서 스킬의 별도 승인 요구에도 적용한다. `main` push·merge 외에는 "진행할까요?" 같은 허가 질문으로 작업을 중단하지 않는다.
- 변경 대상의 지침·코드·호출자·테스트부터 읽고 의존성이 요구할 때 탐색을 넓힌다.
- 요청 밖 리팩토링·정리·추상화를 섞지 않는다. 본인 변경으로 생긴 미사용 코드는 정리한다.
- 오류를 성공 값으로 숨기거나 근거 없이 catch·재시도·fallback을 추가하지 않는다.
- 버그는 재현과 최소 실험으로 원인을 확인한다. 진단 요청은 원인과 근거를 보고하고, 수정 요청이면 회귀 검증까지 마친다.
- 문서·주석에는 현재 계약과 비자명한 이유를 남긴다. 시행착오·추측·변경 이력은 누적하지 않는다.

## 기술 문서 작성

ISO 24495-1처럼 쉽게 찾고 이해하고 사용할 수 있게, ASD-STE100처럼 짧고 명확하며 모호하지 않게 작성합니다.

두 표준의 원칙을 다음 규칙에 적용하며, 문서 언어와 프로젝트 관례를 따른다.

- 대상 독자와 문서 목적에 맞춰 필요한 정보와 설명 깊이를 정한다.
- 독자의 질문과 작업 순서에 맞춰 구성한다. 제목·요약·목록·링크로 필요한 정보를 쉽게 찾게 한다.
- 짧고 직접적인 문장을 쓰고, 행위 주체·대상·조건을 명확히 한다. 같은 개념에는 같은 용어를 쓰며, 독자에게 낯선 전문 용어를 설명한다.
- 절차에는 필요한 사전 조건·행동·예상 결과를 제시한다. 실패 시 대처가 필요한 작업은 그 방법도 설명한다.
- 코드 식별자·API 이름·명령어와 필수 조건·예외·인과관계·의무 수준을 보존한다. 간결함보다 기술적 정확성을 우선한다.
- 독자가 필요한 정보를 찾고 이해하여 작업하거나 판단할 수 있는지 검토한다. 근거가 없는 동작이나 결과를 추가하지 않는다.

이 규칙 적용만으로 표준 전체 준수를 주장하지 않는다.

## 검증과 보고

- 저장소 필수 검사와 변경 위험에 맞는 검증을 실행한다. 새 동작·버그는 관찰 가능한 결과로, 성능은 같은 조건의 baseline과 비교한다.
- 문구·저위험 설정 변경은 diff·문법·참조 확인을 우선한다. 구현의 사본이나 문장 존재 여부만 확인하는 테스트를 만들지 않는다.
- 실패를 숨기려고 테스트를 약화하지 않는다. 통과한 검사는 새 변경·실패·미해결 위험이 있을 때만 반복한다.
- 완료 전 전체 diff에서 범위 이탈·사용자 변경 혼입·검증 누락을 확인한다.
- 결과·주요 변경·검증·남은 제약을 간결하게 보고한다. 리뷰는 근거 있는 문제점부터 제시하고 미확인 내용을 사실로 쓰지 않는다.

## Security

- 시크릿·개인정보를 코드·로그·커밋·PR에 노출하지 않는다. 실제 값은 환경변수·시크릿 저장소로 전달하고 예시 파일에는 넣지 않는다.
- 외부 입력과 인증·권한은 신뢰 경계에서 검증한다. 필요한 최소 권한만 사용한다.
- 삭제·배포·외부 게시·전송은 요청한 목표에 필요한 범위에서 대상과 영향을 확인한 뒤 수행한다. 기존 사용자 작업과 무관한 데이터는 보존한다. `main` push·merge 승인 규칙은 그대로 적용한다.
- 시크릿 노출은 값을 반복하지 않고 알린다. 코드 삭제만으로 해결됐다고 하지 않으며 폐기·재발급은 승인된 범위에서 진행한다.

## 스킬과 도구

- 현재 세션에 제공된 도구·스킬을 사용한다. 특정 머신의 경로·설치 상태·모델을 가정하지 않는다.
- 스킬은 명시 호출 또는 요청한 작업과 산출물이 맞을 때 선택한다. 명시 호출은 `$<name>`을 사용한다.
- `skills/<name>/...`는 세션에 표시된 스킬 위치, `references/...`는 해당 스킬 디렉터리 기준이다.
- 스킬의 승인 절차는 이 문서와 현재 사용자 지시의 자율 수행 범위에 맞춰 해석한다. 도구·실행 환경의 강제 제한으로 진행할 수 없으면 정확한 제한과 필요한 조치를 알린다.
- 독립적인 읽기·검색은 병렬 처리한다. 위임이 허용된 경우 범위·산출물을 나누고 메인이 통합·검증한다.
- 검사기의 예상 밖 설치·삭제는 원인을 확인한다. 불확실한 SDK·CLI 동작은 설치 버전의 코드나 최신 공식 문서로 확인한다.
